# PR #1 write-up: runner + scorer for one target model

**Verdict up front:** the pipeline is real and mechanically sound — it materializes sandboxes, drives a live model through copperhead, scores the result offline, writes a schema-valid record, and reproduces that verdict with no API key set. What it has *not* done, on either of the two worked tasks, in any of three real runs, is watch the model pass. Two runs stalled, one hit a turn cap. Treat this PR as "the harness works," not as "the harness has a result."

## What this PR implements

This lands the runner (`src/runner/`) and scorer (`src/scorer/`) against the repo's two existing worked tasks — `do-rename-net` and `do-budget-refusal-pullup` — for a single hardcoded target model, covering tasks.md sections 3.1–3.3, 3.5, 4.1–4.6, and 5.1. Concretely: sandbox materialization (fixture copy, `git init`, baseline commit, teardown that preserves the sandbox for later rescoring), run execution that drives copperhead as a subprocess and enforces turn and wall-clock caps, a `--dry-run` plan/cost estimator, resumability (`--force` / skip-if-recorded), the three offline evidence adapters, 14 of the 23 assertion vocabulary types, a deterministic failure classifier covering 6 of 11 STANDARD.md categories, `--rescore`, and result-record writing with the full comparability stamp and a pre-write secret scan. Explicitly out of scope, per the PR description: the aggregate report, failure work queue, `LEADERBOARD.md` generation, and `--compare` regression gating (tasks.md 5.2–5.6) — everything this PR builds writes a result record and stops. Ablation overrides (3.4) are also untouched. The full multi-model matrix (migration-plan step 4) is not built here either; this is one model, not a leaderboard.

## The two rules, and how this PR satisfies them

**Grading never calls a model.** The scorer's evidence comes from exactly three adapters under `src/scorer/evidence/`: `sandbox-state.ts` (kicad-cli ERC/DRC output and the sexp parser reading the sandbox end state), `diff.ts` (`git diff` against the recorded baseline commit), and `transcript.ts` (`.copperhead/runs/<ts>/transcript.jsonl`, including `run-start`/`run-end`). None of `src/scorer/` imports `fetch`, makes an HTTP call, or reads a provider credential — confirmed by grep; the one string that looks credential-shaped (`secrets.ts`'s `openai-anthropic` pattern name) is a regex used to *detect* leaked keys in output, not a call site. `--rescore` (`src/scorer/rescore.ts`) exercises this directly: it re-evaluates a preserved sandbox and transcript with `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` explicitly unset and reproduces the same verdict.

**A task is data.** `src/scorer/assertions.ts` dispatches purely on `assertion.type` from `assertions.json`; the only place a task id appears in that file is inside an error message (`assertions.ts:100`), not a conditional. Nine of the 23 vocabulary types throw a clear not-implemented error rather than silently passing, and a type outside the whole vocabulary is a separate validation error — both worked tasks only exercise the 14 that are implemented, and nothing in the dispatch path special-cases either task by name.

## What model this actually ran against, and why that's a deviation

Every real run in this PR used `compat:qwen2.5-coder:7b` through a local Ollama, via copperhead's `--model compat:<id>` route — an open-weight, self-hosted model with no per-token cost. That is not what the project's own migration plan (`openspec/changes/add-model-benchmark-suite/design.md`, "Migration Plan") describes for this stage. Step 2, which this PR frames itself as completing, calls for the runner and scorer to be "verified offline with a recorded transcript fixture so the scorer has tests that need no provider" — no live model at all. The first live model run is step 4: "the two direct API providers at frontier and cheap tiers" (i.e., paid Anthropic/OpenAI-style endpoints), with the open-weight segment not scheduled until step 5. This PR's real runs instead used a step-5-shaped model ahead of a step-4 run, and did so beyond what step 2 asked for. Neither the PR description nor the commit history states a reason for the substitution (no mention of cost, credentials, or availability) — worth asking the author directly rather than assuming.

## Real run results — read this section, not the checkbox

Three real result records exist under `results/2026-08-01/compat-qwen2.5-coder-7b/`, all produced through the actual `npm run benchmark` pipeline against the live model, not synthetic transcripts:

- **`do-rename-net/run-1.json`**: exit path `stalled` — the model made 3 tool-call turns (9,551 tokens in / 210 out, ~4.5 minutes), then stopped emitting tool calls and copperhead's stall detector ended the run. No net was renamed, no commit was made. `verdict.pass: false`, `partialCredit: 0.5` (6 of 12 assertions passed, all structural — ERC/DRC-no-new-violations, diff-ratio, file-unchanged — none of the ones that actually require the edit).
- **`do-rename-net/run-2.json`**: exit path `turn-budget-exhausted`, deliberately run with `maxTurns: 1` to confirm the classifier maps that exit path correctly rather than to test the model. Same `pass: false`, `partialCredit: 0.5`.
- **`do-budget-refusal-pullup/run-1.json`**: exit path `stalled` — 3 turns, 10,151 in / 626 out tokens, ~8 minutes, then the same stall pattern. The task wants a well-formed refusal citing the budget; the model neither refused correctly nor made the change, so `refused` and `refusal-cites-the-budget` both fail. `pass: false`, `partialCredit: 0.5`.

None of the three is a pass, and none is even a clean failure in the sense of "the model tried and got it wrong" — two of three ended because the model simply stopped acting, and the third was an intentionally short leash used to test the classifier rather than the model. Do not read "3 runs, all schema-valid, all correctly classified" as a proxy for "the pipeline is validated end to end against real model behavior" — it validates the *plumbing* end to end; it says nothing yet about whether this model, or any model, can pass either task in this harness.

## The copperhead bug this PR's testing surfaced

copperbench's own real-fixture runs are what found chouhanindustries/copperhead#164 (open, not yet merged): `normalizeReport()` in copperhead computed ERC/DRC `ok` as zero-violations-of-any-kind rather than zero-*error*-severity-violations, and `finish({outcome:'done'})` refused unconditionally unless both reports were `ok`. Every real KiCad board vendored by copperbench carries permanent library-resolution *warnings* at baseline (the `antmicro-microphone-board` fixture used by both worked tasks: 44 ERC / 13 DRC warnings, zero errors) — copperbench's own STANDARD.md decisions D21/D23 already document this as unavoidable and account for it via baseline-relative assertions rather than requiring a clean report. copperhead's internal gate had no equivalent carve-out, so any `do` run that touched a real fixture would burn its entire repair-cycle budget on unfixable warnings and end `repair-cycles-exhausted` regardless of model quality — a result that would have silently invalidated any pass-rate claim made against this fixture. copperbench's live runs against `do-rename-net` are cited directly in #164 as the evidence that motivated the fix (both runs ended for unrelated reasons — `stalled` / `turn-budget-exhausted` — rather than `repair-cycles-exhausted`, confirming the fix removes the blocking failure mode). The fix is in a separate, currently open PR: https://github.com/chouhanindustries/copperhead/pull/164.

## What's still unverified

Be clear-eyed about this: no run in this PR has produced a genuine model success on either worked task. The pipeline's mechanics are proven — sandbox materializes correctly, the model runs, the scorer grades offline from the three evidence sources with no model or network call, a schema-valid record is written, and `--rescore` reproduces the identical verdict (including failure category, per commit `c3b9fc5`'s strengthening of that comparison) with no provider credential present. What has not been observed even once is a model completing either task correctly, or issuing a well-formed refusal on the refusal task. That is a finding about `compat:qwen2.5-coder:7b` in this harness, and arguably it's informative on its own, but it should not be mistaken for "the benchmark works and here's a result" — there is no result yet, only a working measuring instrument.

## CI / verification status

There is no GitHub Actions workflow in this repository (`.github/workflows/` doesn't exist), so nothing about this PR has been checked by an independent CI run — no required check, no separate machine, no protection against "works on my machine." `npm run typecheck` passes clean on the current tip (`60f5e81`) with no output. `npm test` (81 tests, 12 files, per the commit history) is mostly green but not unconditionally: a full-suite run on this same commit produced 2 failures, both in `test/scorer/rescore.test.ts` — one a 60-second timeout, one hitting the classifier's deliberate throw-rather-than-guess path on an exit-path/assertion combination it doesn't have a confirmed mapping for. Re-running that file alone immediately after passed both tests cleanly. This is consistent with the flakiness this project has already documented for its subprocess-heavy integration tests (git/copperhead-init/kicad-cli under parallel load — the reason `vitest.config.ts` disables file parallelism at all), not a new regression, but it means "npm test passes" is true on a clean, isolated run and not guaranteed true of every invocation — worth knowing before treating a red run as a real break.
