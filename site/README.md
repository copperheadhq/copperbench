# site/

The copperbench website, leaderboard first. An [Astro](https://astro.build/) project with no integrations, built statically. Every page is generated from the repository: the front page carries the leaderboard, and the standard, the fixture standard, each task, each fixture, each result record and the price table have pages of their own, so the sidebar never sends a reader to GitHub for something the repository already says.

`npm run site` renders `site/dist/` from the repository as checked out. Nothing on the page is typed by hand:

- The leaderboard, the discrimination check and every record count come from `results/` through [scripts/lib/leaderboard.ts](../scripts/lib/leaderboard.ts), the same aggregation `LEADERBOARD.md` and the paper tables will read. Records whose comparability stamp disagrees with the checked-out suite are listed with their reason and never averaged into a row.
- Task counts per tier come from `tasks/`, the fixture table from `fixtures/*/fixture.json`, the suite and schema versions from `scripts/lib/record.ts` and the build commit from git. All of it is read once per build by [scripts/lib/site-facts.ts](../scripts/lib/site-facts.ts), which lives under the root `tsconfig.json` and is tested in `test/leaderboard.test.ts`. The `.astro` files under `src/` only format what it returns.
- The repository's own markdown is rendered as checked in: `STANDARD.md` at `/standard`, `fixtures/FIXTURES.md` at `/fixtures`, each `tasks/<id>/README.md` at `/tasks/<id>` and each `fixtures/<id>/README.md` at `/fixtures/<id>`, through a content collection in [src/content.config.ts](src/content.config.ts) whose base is the repository root. Heading ids are GitHub's slugs, so a `STANDARD.md#7-scoring` link works in both places. A relative link inside one of those documents is rewritten at build time by the plugin in [astro.config.mjs](astro.config.mjs): to the page that renders the target when the site has one, to GitHub otherwise. The map of which repository paths have pages is [scripts/lib/site-routes.ts](../scripts/lib/site-routes.ts), and every link the components emit goes through it too (`src/lib/links.ts`).
- Each result record has a page at `/results/<date>/<model>/<task>/run-<n>` showing its assertions and comparability stamps beside the checked-out suite's values, with the raw JSON served beside it at the same path plus `.json`. `/pricing.json` and `/leaderboard.json` serve the price table and the aggregated leaderboard the same way.
- Every href is relative to the page it appears on, so one build serves at a domain root or under a path. A nested page such as a record climbs back with `../` per segment; `relativeHref` in `site-routes.ts` is the one place that arithmetic lives, and `test/site.test.ts` pins it.
- The only editorial input is [status.json](status.json), the timeline of what is done and what is next. Keep it free of numerals. A quantity belongs in a generated cell, not in prose that will go stale. A test enforces this.
- The "Paper" links point at the built PDF, not at the LaTeX source. `paper/main.pdf` is gitignored and the Cloudflare build machine has no LaTeX, so [.github/workflows/paper.yml](../.github/workflows/paper.yml) builds it with `npm run paper:pdf` on every push to `main` that touches `paper/` and force-pushes the one file, as `copperbench.pdf`, to the orphan branch `paper-pdf`, where GitHub renders it inline. `paperPdf` in [src/lib/facts.ts](src/lib/facts.ts) is the only place the site spells that address. Until the workflow has run once on `main` the link is a 404; `workflow_dispatch` runs it by hand.

`site/dist/` is derived and gitignored. It is served by a Cloudflare Worker as static assets, configured in [wrangler.jsonc](../wrangler.jsonc) at the repository root, and deployed by Cloudflare's GitHub integration rather than by a workflow in this repository. Connect it once in the Cloudflare dashboard, Workers & Pages → Create → Import a repository, with these settings:

| Setting | Value |
| --- | --- |
| Root directory | `/` |
| Build command | leave empty |
| Deploy command | `npx wrangler deploy` |
| Non-production branch deploy command | `npx wrangler versions upload` |
| Production branch | `main` |

The site lives at `https://copperbench.org/`, committed as `site` in [astro.config.mjs](astro.config.mjs) so the canonical and Open Graph URLs are absolute, which link previews require. `SITE_URL` in the build environment overrides it for a build that serves elsewhere; a value without a scheme or trailing slash is normalized. The custom domain is declared in `wrangler.jsonc` and needs the zone on the same Cloudflare account.

Cloudflare installs with `npm ci`, runs the build through wrangler's `build.command`, reads the Node version from [.node-version](../.node-version) (Astro needs 22.12 or newer; the rest of the repository runs on 20), and takes the Worker name and asset directory from `wrangler.jsonc`. Every push to `main` deploys. Every other branch and pull request gets a preview version on its own workers.dev URL, reported as a check on the commit. Production serves at copperbench.org. `npm run site:deploy` deploys from a machine after `npx wrangler login`.

`npm run site:dev` (or `npm run dev`, its alias at the repository root) runs Astro's dev server with live reload. `npm run site:serve` builds and previews `site/dist/`. The rendered page loads nothing from any CDN and ships no client JavaScript beyond the tier tabs and the route filter. The typefaces are the Fontsource packages the copperhead docs ship, Inter Variable and IBM Plex Mono, copied into `public/fonts/` by [copy-fonts.mjs](copy-fonts.mjs) before each build. The Open Graph image, `public/og.png`, is rendered before each build by [og.mjs](og.mjs) from an inline SVG set in the same Inter, so it needs no system font and is never committed.

Type, sizing, color and icons follow the copperhead sites so the two read as one project: the same fonts, Starlight's type scale and line heights, the same gray ramp and copper accent, and the same fiducial mark on the same dark tile for the favicon, touch icon and manifest icons in `public/`. The layout follows the leaderboard-first shape benchmark sites converge on. Both are in [public/styles.css](public/styles.css).
